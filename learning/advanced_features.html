Advanced Features

Four features added on top of the base pipeline: lighting/color matching (garments no longer keep their studio lighting), lower-body support (pants/skirts, not just shirts), a --debug mode (see exactly what the pipeline detected), and a multi-garment comparison grid (try several outfits against one photo at once). CLI: python main.py --person p.jpg --cloth a.jpg b.jpg --garment-type auto --debug
▶match_lighting() — Reinhard-style color transfer tryon/lighting.py

Product photos are shot under flat studio light; a person's photo almost never is. Without correction, a warped garment keeps its studio brightness/color and visibly "floats" on the person even after blending. This shifts the garment's color statistics (mean & spread, per channel) to match the lighting already present at the spot it's being placed onto.

Core idea (LAB color space)
src_lab = cv2.cvtColor(garment_bgr, cv2.COLOR_BGR2LAB).astype(np.float32)
dst_lab = cv2.cvtColor(person_bgr, cv2.COLOR_BGR2LAB).astype(np.float32)

for channel in range(3):                       # L (lightness), A, B (color)
    src_vals = src_lab[:, :, channel][src_mask]  # garment pixels only
    dst_vals = dst_lab[:, :, channel][dst_mask]  # person's torso-area pixels only
    src_mean, src_std = src_vals.mean(), src_vals.std()
    dst_mean, dst_std = dst_vals.mean(), dst_vals.std()

    channel_data = src_lab[:, :, channel]
    result[:, :, channel] = (channel_data - src_mean) * (dst_std / src_std) + dst_mean
Why LAB, not BGR

LAB separates brightness (L) from color (A=green-red, B=blue-yellow). That means "make it darker like the person's lighting" and "make it warmer/cooler like the person's lighting" can be adjusted independently and cleanly — doing the same statistic-matching directly in BGR would tangle brightness and color together and look worse.

Why only sample masked pixels

src_mask/dst_mask restrict the mean/std computation to real garment pixels (not its transparent background) and to the actual blend region on the person (not the whole photo, which might include a bright wall or dark background that would skew the target lighting incorrectly).

When to reach for this technique
  • Compositing any two images shot under different lighting — object insertion, "photobashing," harmonizing a cut-out sticker into a scene, day/night image conversion.
This is the same family of technique as "Reinhard color transfer" (Reinhard et al., 2001) — a classic, cheap alternative to training a neural style-transfer model when you just need statistics to roughly line up.
▶LegLandmarks & detect_legs() — lower-body support tryon/pose.py

The original pipeline only fit garments to the torso (shoulders → hips), so it could only try on shirts/jackets. This adds a second landmark set — hips → ankles — so pants and skirts warp onto the legs instead.

Used in this project
def as_quad(self, waist_lift=0.08, ankle_drop=0.05):
    lh, rh, la, ra = self.left_hip, self.right_hip, self.left_ankle, self.right_ankle
    leg_h = np.linalg.norm(((la + ra) / 2) - ((lh + rh) / 2))
    up = np.array([0, -1.0]) * leg_h * waist_lift     # a bit above the hips, for the waistband
    down = np.array([0, 1.0]) * leg_h * ankle_drop     # a bit past the ankles, for the hem
    ...

This mirrors TorsoLandmarks.as_quad() exactly, just anchored to different joints — the same "expand the quad slightly past the literal joint positions" trick, because clothing always extends a bit beyond the skeleton (a waistband sits above the hip joint, a shirt collar sits above the shoulder joint).

Auto garment-type detection
def _guess_garment_type(self, src_quad):
    width = np.linalg.norm(src_quad[1] - src_quad[0])
    height = np.linalg.norm(src_quad[3] - src_quad[0])
    return "lower" if height / width > 1.4 else "upper"

A cheap heuristic (not a classifier): pants/skirts are usually noticeably taller than wide in a front-facing product photo, shirts are closer to square. Override it with --garment-type upper|lower when it guesses wrong.

▶draw_quad() & cv2.polylines / cv2.circle / cv2.putText tryon/debug_viz.py

--debug saves an image showing exactly which 4 points the pipeline computed for the target body region — so if a result looks wrong, you can immediately tell whether pose detection was off, versus a warping/blending problem.

Used in this project
cv2.polylines(out, [pts], isClosed=True, color=color, thickness=2)  # outline the quad
for (x, y) in pts:
    cv2.circle(out, (x, y), 5, color, -1)                            # mark each corner
cv2.putText(out, label, (pts[0][0], pts[0][1] - 12),
            cv2.FONT_HERSHEY_SIMPLEX, 0.6, color, 2, cv2.LINE_AA)     # e.g. "upper" / "lower"
When to reach for these
  • cv2.polylines — outlining any polygon: detected quads, contours, ROI boundaries.
  • cv2.circle — marking individual points: keypoints, landmarks, click locations.
  • cv2.putText — burning readable labels/debug info directly into an image so it's self-documenting when shared or saved.
These three are the bread-and-butter of any CV debugging workflow — draw what the algorithm "thinks it sees" on top of the real image, rather than trying to debug from raw numbers.
▶mask_overlay() & cv2.addWeighted-style blending tryon/debug_viz.py

Tints an image with a translucent color wherever a mask is active — used to visualize the final blend mask (where the garment will actually be painted) as a green highlight over the person photo.

Used in this project
mask3 = np.clip(mask, 0, 1)[:, :, None]
tinted = (image_bgr.astype(np.float32) * (1 - mask3 * alpha) +
          color_layer.astype(np.float32) * (mask3 * alpha)).astype(np.uint8)

This is the manual equivalent of OpenCV's built-in cv2.addWeighted(src1, alpha, src2, beta, gamma), done per-pixel with a spatially-varying alpha (built-in addWeighted only supports one global blend weight for the whole image, not a per-pixel mask).

When to reach for it
  • Visualizing any mask/heatmap/segmentation result on top of the original image — the standard way to "see" what a mask covers instead of looking at a separate black-and-white image.
▶make_comparison_grid() — cv2.resize, cv2.copyMakeBorder, cv2.hconcat main.py

When multiple --cloth images are passed, this builds one side-by-side image (original + every try-on result, each labeled) instead of making you open several files to compare outfits — directly serving the "check clothes before buying" goal when comparing options.

Used in this project
scale = tile_height / img.shape[0]
tile = cv2.resize(img, (int(img.shape[1] * scale), tile_height))          # normalize every tile to the same height
tile = cv2.copyMakeBorder(tile, 0, 36, 0, 0, cv2.BORDER_CONSTANT, value=(30, 30, 30))  # add a label strip
cv2.putText(tile, label, (8, tile.shape[0] - 12), ...)
...
grid = cv2.hconcat(padded)   # glue all tiles into one wide image
Function reference
  • cv2.resize(img, (w, h)) — change an image's pixel dimensions; here used to make every result the same height before concatenating.
  • cv2.copyMakeBorder(src, top, bottom, left, right, borderType, value) — pad an image with a solid color border; here it reserves space at the bottom for a text label, and later pads narrower tiles to a common width.
  • cv2.hconcat([img1, img2, ...]) — stitch images of the same height side by side into one wide image (there's a matching cv2.vconcat for stacking images of the same width vertically).
When to reach for these
  • Building contact sheets, before/after comparisons, thumbnail grids, or any "many small images → one summary image" output.
hconcat/vconcat require every input to already match on the non-concatenated dimension (same height for hconcat, same width for vconcat) — that's why the code resizes and pads first.
Case study. The two entries below aren't hypothetical — they're bugs found by actually running the pipeline on a real photo (a chest-up headshot) and a real product photo (a shirt hanging from a wooden hanger), and reading the intermediate debug images to see exactly where it broke.
▶Landmark .visibility — don't trust extrapolated joints tryon/pose.py

Every mediapipe landmark carries a .visibility score (0–1), not just an (x, y) position. When a joint is actually out of frame — e.g. the hips in a chest-up headshot — mediapipe still returns coordinates for it (the model always outputs all 33 points), but they're a low-confidence guess, not an observation.

What actually happened

Running the pipeline on a real bust-photo, the hip landmarks came back at visibility ≈ 0.25–0.31 and collapsed toward the image center instead of spreading to plausible hip positions. Feeding that straight into the torso quad produced a near-triangular target region; warping a rectangular shirt image into a triangle is a near-singular homography, which exploded into a huge blurry blob covering half the photo.

The fix
VISIBILITY_THRESHOLD = 0.5

if left_hip_vis < VISIBILITY_THRESHOLD or right_hip_vis < VISIBILITY_THRESHOLD:
    # Hips aren't reliably visible -- synthesize a plausible hip line from
    # the shoulders instead of trusting mediapipe's low-confidence guess.
    shoulder_vec = right_shoulder - left_shoulder
    shoulder_width = np.linalg.norm(shoulder_vec)
    perp = np.array([-shoulder_vec[1], shoulder_vec[0]])   # perpendicular to the shoulder line
    if perp[1] < 0:
        perp = -perp                                        # make sure it points down the image
    down_dir = perp / np.linalg.norm(perp)
    hip_mid = shoulder_mid + down_dir * shoulder_width * 1.35   # typical torso-height:shoulder-width ratio
    ...
The general lesson
  • Any model that outputs a confidence/visibility score alongside a prediction is telling you when to not trust that prediction — checking only "did it return a value" isn't the same as checking "is this value real."
  • Getting a rotated perpendicular to a 2D vector (dx, dy) is just (-dy, dx) or (dy, -dx) — pick whichever one points the direction you need (here, checked with if perp[1] < 0 since image y grows downward).
This still isn't a real measurement — it's a plausible fallback. A photo that actually shows the torso will always fit better than one where the hips had to be guessed.
▶strip_hanger() — a segmentation model can't tell "clothing" from "prop" tryon/garment.py

Background removal (rembg) does foreground/background segmentation — it isolates "the salient object," not specifically "the garment." A shirt photographed on a wooden hanger produces one connected foreground blob: hook, hanger bar, and shirt, all equally "foreground." Two different rembg models (a 4.7MB one and a 176MB one) both kept the hanger — swapping models doesn't fix this, because it's not a quality problem, it's a category the model was never asked to distinguish.

What actually happened

The garment-quad detector originally scanned a thin band near the top of the mask to find "shoulder width." The hanger's hook is only a few pixels wide right at the top, so it got measured as the shoulder width — producing a source rectangle far narrower than the real shirt, and a wildly skewed warp. The result: the hanger, badly stretched, rendered directly on the person's chest.

The fix — verified empirically, not guessed
# Printed the mask's per-row pixel width near the top to see the actual
# shape of the problem before writing any fix:
for y in range(y_min, y_min + 140, 4):
    cols = np.where(mask[y, :] > 0)[0]
    print(y, cols.max() - cols.min())
# -> width grew continuously from ~7px (hook) with no clean break before
#    the real shoulders -- ruled out any "find the width jump" heuristic.

# Rendered the mask with different top crop fractions and looked at each
# one directly, instead of assuming a number:
for frac in [0.10, 0.13, 0.15, 0.18, 0.20]:
    test = mask.copy()
    test[:int(h * frac), :] = 0
    cv2.imwrite(f'debug_{frac}.png', test * 255)
# -> 0.10-0.15 all fully cleared the hook+hanger in the actual test photo
def strip_hanger(garment_bgra, top_frac=0.16):
    alpha = garment_bgra[:, :, 3]
    ys, _ = np.where(alpha > 10)
    y_min, y_max = ys.min(), ys.max()
    cutoff = int(y_min + (y_max - y_min) * top_frac)
    result = garment_bgra.copy()
    result[:cutoff, :, 3] = 0     # discard everything above the cutoff
    return result
The general lesson
  • Don't guess a magic-number threshold and move on — render the intermediate result and actually look at it. The right value here (0.16, not an arbitrary "looks about right" guess) came from comparing several crop levels side by side.
  • This is a blunt heuristic with a known cost: a garment photo with no hanger (flat lay, worn on a model) loses a bit of real top-of-garment area for no benefit. Documented as a known trade-off rather than hidden — a fix that works for the tested case but silently breaks another case is worse than an honest limitation.
  • When a general-purpose model (segmentation, detection, classification) doesn't distinguish the category you actually care about, no amount of picking a "better" pretrained model fixes it — you need a task-specific step on top, or a model trained specifically for that distinction.
Two more controls added on top of the warp/blend engine: --flip-garment (mirror a garment shot facing the wrong way) and --opacity (fade the composite back toward the original photo). CLI: python main.py --person p.jpg --cloth shirt.jpg --flip-garment --opacity 0.5
▶cv2.flip(img, 1) — mirroring a garment that faces the wrong way tryon/classic_backend.py

Product photos aren't consistently shot facing one direction — a shirt photographed at a slight three-quarter angle facing right won't line up as well onto a person facing left. Rather than trying to detect and auto-correct this, --flip-garment just lets the user mirror the garment and re-run.

Used in this project
garment_bgra = strip_hanger(garment_bgra)
if self.flip_garment:
    garment_bgra = cv2.flip(garment_bgra, 1)   # 1 = horizontal flip
src_quad = garment_quad(garment_bgra)          # computed *after* flipping
Why order matters here

The flip happens before garment_quad() runs, not after — the quad (and every downstream step: homography, warp, lighting match) needs to be computed from the already-mirrored garment, otherwise the flip would just undo itself visually once warped onto the same target region.

cv2.flip flip codes
  • 0 — flip vertically (around the horizontal axis, top ↔ bottom).
  • 1 — flip horizontally (around the vertical axis, left ↔ right) — used here.
  • -1 — flip both axes (180° rotation).
When to reach for it
  • Any time an asset's handedness/orientation doesn't match the target it's being composited onto, and there's no reliable automatic way to detect that mismatch.
▶Opacity fade — why it has to happen after seamlessClone, not inside it tryon/classic_backend.py

--opacity lets the composite be faded back toward the original, untouched photo — useful for a subtler "does this roughly work" preview, or to sanity-check garment alignment before committing to a full-strength blend.

The naive approach doesn't work

The obvious idea — multiply combined_mask by opacity and feed that weaker mask straight into cv2.seamlessClone — doesn't do what it sounds like. seamlessClone treats its mask as a hard region (any nonzero pixel counts as "inside the region to clone"), not a per-pixel blend weight; it isn't designed for partial-strength compositing at all.

The actual fix — fade the finished result
result = cv2.seamlessClone(warped_rgb, person_bgr, mask_u8, center, cv2.NORMAL_CLONE)

if self.opacity < 1.0:
    fade = (combined_mask * self.opacity)[:, :, None]
    result = (result.astype(np.float32) * fade +
              person_bgr.astype(np.float32) * (1 - fade)).astype(np.uint8)

Run the full-strength seamless clone first, exactly as before, then linearly blend that finished result back toward the original person photo — weighted by combined_mask (so the fade only affects the region the garment actually landed on, not the whole photo) scaled by opacity.

Verified, not assumed

Checked with an actual pixel-difference measurement across three runs of the same photo/garment pair: --opacity 0 came back nearly identical to the original photo (mean diff ≈0.2/255, just JPEG re-encoding noise), --opacity 0.5 landed roughly halfway between the original and the full-strength result, and --opacity 1 (the default) matched the pre-existing full-strength output — confirming the fade is linear and correctly anchored, not just "looks about right."

The general lesson
  • A function's mask/weight parameter isn't automatically a graded blend weight just because it accepts float/graded input — check what the function actually does with intermediate values (here, seamlessClone silently treats "10% opacity" the same as "100%"), rather than assuming.
  • When a built-in can't do what you need directly, it's often simpler to run it as designed and post-process the result, rather than fighting its API to make it do something it wasn't built for.
