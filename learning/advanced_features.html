Advanced Features

Four features added on top of the base pipeline: lighting/color matching (garments no longer keep their studio lighting), lower-body support (pants/skirts, not just shirts), a --debug mode (see exactly what the pipeline detected), and a multi-garment comparison grid (try several outfits against one photo at once). CLI: python main.py --person p.jpg --cloth a.jpg b.jpg --garment-type auto --debug
▶match_lighting() — Reinhard-style color transfer tryon/lighting.py

Product photos are shot under flat studio light; a person's photo almost never is. Without correction, a warped garment keeps its studio brightness/color and visibly "floats" on the person even after blending. This shifts the garment's color statistics (mean & spread, per channel) to match the lighting already present at the spot it's being placed onto.

Core idea (LAB color space)
src_lab = cv2.cvtColor(garment_bgr, cv2.COLOR_BGR2LAB).astype(np.float32)
dst_lab = cv2.cvtColor(person_bgr, cv2.COLOR_BGR2LAB).astype(np.float32)

for channel in range(3):                       # L (lightness), A, B (color)
    src_vals = src_lab[:, :, channel][src_mask]  # garment pixels only
    dst_vals = dst_lab[:, :, channel][dst_mask]  # person's torso-area pixels only
    src_mean, src_std = src_vals.mean(), src_vals.std()
    dst_mean, dst_std = dst_vals.mean(), dst_vals.std()

    channel_data = src_lab[:, :, channel]
    result[:, :, channel] = (channel_data - src_mean) * (dst_std / src_std) + dst_mean
Why LAB, not BGR

LAB separates brightness (L) from color (A=green-red, B=blue-yellow). That means "make it darker like the person's lighting" and "make it warmer/cooler like the person's lighting" can be adjusted independently and cleanly — doing the same statistic-matching directly in BGR would tangle brightness and color together and look worse.

Why only sample masked pixels

src_mask/dst_mask restrict the mean/std computation to real garment pixels (not its transparent background) and to the actual blend region on the person (not the whole photo, which might include a bright wall or dark background that would skew the target lighting incorrectly).

When to reach for this technique
  • Compositing any two images shot under different lighting — object insertion, "photobashing," harmonizing a cut-out sticker into a scene, day/night image conversion.
This is the same family of technique as "Reinhard color transfer" (Reinhard et al., 2001) — a classic, cheap alternative to training a neural style-transfer model when you just need statistics to roughly line up.
▶LegLandmarks & detect_legs() — lower-body support tryon/pose.py

The original pipeline only fit garments to the torso (shoulders → hips), so it could only try on shirts/jackets. This adds a second landmark set — hips → ankles — so pants and skirts warp onto the legs instead.

Used in this project
def as_quad(self, waist_lift=0.08, ankle_drop=0.05):
    lh, rh, la, ra = self.left_hip, self.right_hip, self.left_ankle, self.right_ankle
    leg_h = np.linalg.norm(((la + ra) / 2) - ((lh + rh) / 2))
    up = np.array([0, -1.0]) * leg_h * waist_lift     # a bit above the hips, for the waistband
    down = np.array([0, 1.0]) * leg_h * ankle_drop     # a bit past the ankles, for the hem
    ...

This mirrors TorsoLandmarks.as_quad() exactly, just anchored to different joints — the same "expand the quad slightly past the literal joint positions" trick, because clothing always extends a bit beyond the skeleton (a waistband sits above the hip joint, a shirt collar sits above the shoulder joint).

Auto garment-type detection
def _guess_garment_type(self, src_quad):
    width = np.linalg.norm(src_quad[1] - src_quad[0])
    height = np.linalg.norm(src_quad[3] - src_quad[0])
    return "lower" if height / width > 1.4 else "upper"

A cheap heuristic (not a classifier): pants/skirts are usually noticeably taller than wide in a front-facing product photo, shirts are closer to square. Override it with --garment-type upper|lower when it guesses wrong.

▶draw_quad() & cv2.polylines / cv2.circle / cv2.putText tryon/debug_viz.py

--debug saves an image showing exactly which 4 points the pipeline computed for the target body region — so if a result looks wrong, you can immediately tell whether pose detection was off, versus a warping/blending problem.

Used in this project
cv2.polylines(out, [pts], isClosed=True, color=color, thickness=2)  # outline the quad
for (x, y) in pts:
    cv2.circle(out, (x, y), 5, color, -1)                            # mark each corner
cv2.putText(out, label, (pts[0][0], pts[0][1] - 12),
            cv2.FONT_HERSHEY_SIMPLEX, 0.6, color, 2, cv2.LINE_AA)     # e.g. "upper" / "lower"
When to reach for these
  • cv2.polylines — outlining any polygon: detected quads, contours, ROI boundaries.
  • cv2.circle — marking individual points: keypoints, landmarks, click locations.
  • cv2.putText — burning readable labels/debug info directly into an image so it's self-documenting when shared or saved.
These three are the bread-and-butter of any CV debugging workflow — draw what the algorithm "thinks it sees" on top of the real image, rather than trying to debug from raw numbers.
▶mask_overlay() & cv2.addWeighted-style blending tryon/debug_viz.py

Tints an image with a translucent color wherever a mask is active — used to visualize the final blend mask (where the garment will actually be painted) as a green highlight over the person photo.

Used in this project
mask3 = np.clip(mask, 0, 1)[:, :, None]
tinted = (image_bgr.astype(np.float32) * (1 - mask3 * alpha) +
          color_layer.astype(np.float32) * (mask3 * alpha)).astype(np.uint8)

This is the manual equivalent of OpenCV's built-in cv2.addWeighted(src1, alpha, src2, beta, gamma), done per-pixel with a spatially-varying alpha (built-in addWeighted only supports one global blend weight for the whole image, not a per-pixel mask).

When to reach for it
  • Visualizing any mask/heatmap/segmentation result on top of the original image — the standard way to "see" what a mask covers instead of looking at a separate black-and-white image.
▶make_comparison_grid() — cv2.resize, cv2.copyMakeBorder, cv2.hconcat main.py

When multiple --cloth images are passed, this builds one side-by-side image (original + every try-on result, each labeled) instead of making you open several files to compare outfits — directly serving the "check clothes before buying" goal when comparing options.

Used in this project
scale = tile_height / img.shape[0]
tile = cv2.resize(img, (int(img.shape[1] * scale), tile_height))          # normalize every tile to the same height
tile = cv2.copyMakeBorder(tile, 0, 36, 0, 0, cv2.BORDER_CONSTANT, value=(30, 30, 30))  # add a label strip
cv2.putText(tile, label, (8, tile.shape[0] - 12), ...)
...
grid = cv2.hconcat(padded)   # glue all tiles into one wide image
Function reference
  • cv2.resize(img, (w, h)) — change an image's pixel dimensions; here used to make every result the same height before concatenating.
  • cv2.copyMakeBorder(src, top, bottom, left, right, borderType, value) — pad an image with a solid color border; here it reserves space at the bottom for a text label, and later pads narrower tiles to a common width.
  • cv2.hconcat([img1, img2, ...]) — stitch images of the same height side by side into one wide image (there's a matching cv2.vconcat for stacking images of the same width vertically).
When to reach for these
  • Building contact sheets, before/after comparisons, thumbnail grids, or any "many small images → one summary image" output.
hconcat/vconcat require every input to already match on the non-concatenated dimension (same height for hconcat, same width for vconcat) — that's why the code resizes and pads first.
